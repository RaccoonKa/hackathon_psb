# Юридический ИИ-ассистент с агентной верификацией и темпоральным поиском

Система построена вокруг **девятиэтапного агентного пайплайна** с жестким контролем галлюцинаций, проверкой численных и темпоральных предпосылок пользователя, разграничением ролей источников («нормативное основание» vs «документ сделки»), гибридным поиском (BM25 + Dense Vector с взвешенным RRF и нейросетевым реранкингом) и двухконтурной верификацией каждого утверждения ответа.

## 1. Ключевые архитектурные особенности

1. **Структурно-адаптивный чанкинг**:
   - Документы разбираются с учетом юридической иерархии (Раздел → Глава → Статья / Раздел договора → Пункт / Часть → Подпункт / Примечание).
   - Чанкинг никогда не смешивает разные статьи закона или крупные разделы договора ради заполнения лимита токенов.
   - Каждый чанк получает префикс `embedding_text`, включающий название документа, пометку об изменении родительского договора (`[ИЗМЕНЕНИЕ ДЛЯ CONTRACT_...]`) и полный иерархический путь.
2. **Темпоральная и версионная осведомленность**:
   - Автоматическое извлечение дат вступления в силу (`effective_from`), утраты силы (`effective_to`) и связей дополнительных соглашений с базовыми договорами (`amends_document_id`).
   - Фильтрация редакций по дате события (`event_date`) и выбор доминирующей редакции (`select_dominant_versions`), исключающий одновременное попадание устаревшей и новой версий одного документа в контекст.
3. **Разграничение назначения источников (`source_kind`)**:
   - Все документы и слоты запроса делятся на **нормативные основания** (`normative` — законы `law` и внутренние акты `internal`) и **документы сделки** (`specific` — договоры `contract`).
   - Система запрещает подтверждать общее нормативное правило текстом конкретного договора и наоборот — подтверждать условия конкретной сделки текстом регламента или закона.
4. **Двухэтапная защита и проверка предпосылок (`Policy Precheck`)**:
   - Детектирование и санитизация Prompt Injection как на входе (`prefilter`), так и внутри найденных фрагментов документов (`precheck`).
   - Детерминированная сверка численных и календарных предпосылок пользователя (`amount`, `term`, `rate`, `date`) с доверенными чанками: разделение статусов `VERIFIED`, `CONTRADICTED` и `UNKNOWN` (отсутствие подтверждения не трактуется как опровержение).
5. **Строгая верификация и регенерация**:
   - Генератор возвращает структурированный JSON (`DraftAnswer`), где каждое утверждение (`Claim`) привязано к конкретным идентификаторам источников (`S1`, `S2`...) и проверяемому слоту.
   - Верификатор проверяет каждое утверждение на дословное подтверждение источником (`supported`, `not_in_source`, `contradicted`) и отдельно оценивает соответствие ответа исходному вопросу (`answer_to_question`: `match`, `mismatch`, `undetermined`).
   - При регенерации подтвержденные утверждения (`supported_locked`) жестко фиксируются на уровне кода (`_enforce_supported_locked`), а неподтвержденные удаляются или исправляются по точным цитатам.

## 3. Подробное описание работы системы

Работа системы делится на два больших контура: **Офлайн-индексация базы знаний** (`build_index.py` и пакет `rag_core.indexing`) и **Онлайн-обработка запроса агентным оркестратором** (`rag_core.generation` и `rag_core.retrieval`).

### Часть I. Индексация и структурно-адаптивный чанкинг (`rag_core/indexing`)

Точка входа индексации — функция `build_indexes()` в файле `build_index.py`. Она последовательно выполняет 5 шагов:

#### Шаг 1. Чтение документов и извлечение метаданных (`parser.py`)
Модуль `load_documents_with_metadata(RAW_DATA_DIR)` рекурсивно обходит директорию с исходными документами (`.txt`, `.md`, `.docx`, `.pdf`). Также поддерживается безопасная распаковка архивов через `safe_extract_zip()` с защитой от Path Traversal, симлинков и превышения лимита в 512 МБ.
- **Извлечение текста**:
  - Для `.docx` используется `python-docx` с обходом параграфов (`CT_P`) и таблиц (`CT_Tbl`, ячейки склеиваются через ` | `), а при сбое срабатывает резервный парсер XML (`_docx_bytes_to_text` через `zipfile` + `ElementTree`).
  - Для `.pdf` используется `pypdf.PdfReader`, который помимо текста строит карту символьных смещений страниц `page_spans = [(char_start, char_end, page_num), ...]`. Это позволяет точно привязать каждый чанк к странице исходного PDF.
- **Типизация документа (`detect_doc_type`)**:
  - По префиксу пути и первым 1500 символам документ относится к одному из трех классов:
    - `law` — кодексы РФ и федеральные законы;
    - `contract` — договоры и дополнительные соглашения;
    - `internal` — внутренние приказы, положения, регламенты, инструкции и служебные записки.
- **Парсинг дат, версий и связей (`parse_dates_and_version`)**:
  - Находит даты утраты силы (`утратил силу с ...`, `действует до ...` без условия пролонгации) → `effective_to`.
  - Находит дату вступления редакции в силу (`редакция от ...`, `вступает в силу с ...`, `применяется с ...`) → `effective_from`. Если в шапке закона указаны будущие редакции (после `export_date`), они автоматически ограничивают верхнюю границу текущей редакции (`effective_to`).
  - Формирует канонические идентификаторы:
    - Для договоров: `contract_<номер>` (например, `contract_15-2024-ар`).
    - Для дополнительных соглашений: распознает паттерн `к договору ... № X`, выставляет `amends_document_id = "contract_X"` и собственный `document_id = "amend_<номер>_<номер_договора>"`.
    - Для остальных документов: `doc_<нормализованное_имя_файла>`.

#### Шаг 2. Иерархический разбор структуры документа (`extract_document_structure`)
Построчный анализатор `classify_heading()` строит дерево документа со стеком пути `path_stack` по 5 уровням иерархии:

| Уровень | Элемент структуры | Примеры заголовков | Формат `provision_id` |
| :--- | :--- | :--- | :--- |
| **0** | Раздел | `Раздел I...`, `Раздел 2...` | `None` |
| **1** | Глава | `Глава 1...`, `Глава IV...` | `None` |
| **2** | Статья закона / Крупный раздел договора | `Статья 13.11. ...`, `3. Порядок расчетов` | `13.11`, `3` |
| **3** | Пункт договора / Часть статьи / Пункт НК РФ / Примечания | `3.2. ...`, `1. ...` (внутри статьи), `Пункт 4.1`, `Примечания` | `3.2`, `13.11.1`, `13.11.прим` |
| **4+** | Подпункт договора / Пункт примечания | `2.2.3. ...`, `1. ...` (внутри примечаний) | `2.2.3`, `13.11.прим.1` |

Важная деталь: элементы нумерованных перечислений со скобкой (`1)`, `2)`, `15.1)`) **намеренно не классифицируются как отдельные заголовки**, чтобы не разрывать единую правовую норму на микро-чанки без контекста. Также отфильтровываются технические врезки справочных систем (`Федеральным законом от ... в статью внесены изменения...`).

#### Шаг 3. Структурно-адаптивный чанкинг (`chunker.py` и `tokenizer_utils.py`)
Все замеры длины выполняются **исключительно в токенах кодировки `cl100k_base` (`tiktoken`)** по полному полю `embedding_text` (которое включает заголовок документа, маркер изменения родительского договора, иерархический путь и сам текст нормы). 

Целевые пороги чанкера:
- `TARGET_MIN_TOKENS = 300` — нижний порог, ниже которого чанк считается маленьким и стремится объединиться с соседями;
- `TARGET_MAX_TOKENS = 600` — целевой верхний размер при склейке соседних пунктов;
- `HARD_MAX_TOKENS = 750` — жесткий предел размера чанка;
- `OVERLAP_TOKENS = 60` — перекрытие между фрагментами при разбиении одного сверхдлинного положения.

Алгоритм `chunk_document_structural()`:
1. **Защита коротких документов**: если документ является дополнительным соглашением (`amends_document_id`) или внутренним письмом/приказом (`document_type == "internal"`) и целиком (вместе с префиксом) укладывается в `750` токенов, он сохраняется **одним цельным чанком**.
2. **Фильтрация «голых» заголовков (`_is_bare_heading_block`)**: блоки, содержащие только название раздела или статьи без текста нормы (за которыми сразу идут подпункты), удаляются как самостоятельные блоки, но их названия остаются в `structure.path` дочерних пунктов.
3. **Каскадное разделение сверхдлинных блоков (`> 750` токенов)**: если одна статья или пункт превышает `750` токенов, функция `_split_text_structurally()` рекурсивно делит текст по приоритету смысловых границ:
   - Стадия 0: вложенные подпункты (`1.1.1`, `1)`);
   - Стадия 1: элементы списков (`а)`, `-`, `•`);
   - Стадия 2: абзацы (пустые строки) с добавлением перекрытия `60` токенов (`_apply_overlap`);
   - Стадия 3: границы предложений (регулярное выражение исключает точки внутри номеров статей и пунктов вроде `ст. 13.11`) с перекрытием `60` токенов;
   - Стадия 4 (крайний случай): токенный сплиттер `RecursiveCharacterTextSplitter`.
4. **Умная склейка маленьких блоков (`_build_chunk_specs` и `_balance_specs`)**:
   - Соседние короткие пункты склеиваются в один чанк до `600` токенов (или до `750`, если текущий буфер меньше `300` токенов), **только если они принадлежат одному крупному разделу** (имеют одинаковый `section_key` на уровне `<= 2`, т.е. одну статью закона или один раздел договора).
   - Положения из разных статей закона или разных разделов договора никогда не сливаются между собой (единственное исключение — короткая преамбула `< 300` токенов может присоединиться к первому разделу).
   - При склейке нескольких пунктов одной статьи `structure.path` вычисляется как наибольший общий префикс (`_common_path`), а текст берется непрерывным срезом из исходного документа (`_slice_group_text`), сохраняя точные координаты `char_start`, `char_end`, `start_line`, `end_line` и `page`.
5. **Детерминированный идентификатор чанка (`generate_chunk_id`)**:
   - Вычисляется как `{version_id}_{chunk_index:04d}_{sha256[:8]}`, где хеш зависит от `doc_id`, `ver_id`, `source_hash`, `chunker_version` и порядкового номера.

#### Шаг 4. Построение индексов и манифеста (`build_index.py`)
1. Канонический корпус чанков записывается в `data/processed/chunks.jsonl`.
2. **BM25 индекс (`BM25KeywordStore`)**: токенизирует `embedding_text` каждого чанка регулярным выражением `[A-Za-zА-Яа-яЁё0-9]+` в нижнем регистре, строит `BM25Okapi` и сериализует его в `storage/bm25_index/bm25.pkl`.
3. **Векторный индекс (`vector_store.py`)**: очищает коллекцию `document_chunks` в персистентном ChromaDB (`storage/chroma_db`, метрика `cosine`), батчами отправляет `embedding_text` на HTTP-сервер эмбеддингов (`POST {EMBEDDING_API_BASE_URL}/embeddings`, модель `bge-m3`, размерность `1024`), выполняет L2-нормализацию векторов и сохраняет их вместе со скалярными метаданными.
4. **Манифест индексации**: сохраняет статистику распределения токенов и список документов в `data/manifests/indexing_manifest.json`.

### Часть II. Онлайн-пайплайн: Девятиэтапный агентный цикл (`rag_core/generation` и `rag_core/retrieval`)

Внешний код вызывает фасад `rag_core.ask(query, chat_history=..., event_date=..., selected_doc_ids=...)` или напрямую `run_agent()` из `rag_core/generation/orchestrator.py`.

На весь запрос выделяется глобальный дедлайн `REQUEST_TOTAL_TIMEOUT_S` (по умолчанию 90 с) и бюджет ошибок LLM `MAX_LLM_FAILURES_PER_REQUEST` (12 ошибок). Каждый этап записывает телеметрию (входы, выходы, время в миллисекундах, потраченные токены, флаги деградации) в список ` TraceStep`.

Ниже подробно описано прохождение запроса через все стадии (`stage_idx` от `0` до `8`).

#### Стадия 0. Предварительная фильтрация (`prefilter.py`, `stage_idx = 0`)
Быстрый детерминированный фильтр на регулярных выражениях (`run_prefilter`), работающий за доли миллисекунды без обращения к LLM:
1. **Prompt Injection (`_INJECTION_PATTERNS`)**: перехватывает команды вида *«игнорируй предыдущие инструкции»*, *«ты теперь не юрист»*, *«system override»* и мгновенно возвращает отказ `RESPONSE_PROMPT_INJECTION`.
2. **Противоправные запросы (`_ILLEGAL_PATTERNS`)**: блокирует вопросы о подделке договоров/печатей, даче взяток, схемах обналичивания, обходе закона или взломе → возвращает `RESPONSE_ILLEGAL`.
3. **Вопросы о самом ассистенте и Off-topic**: если в запросе **нет юридических маркеров** (`_LEGAL_DOMAIN_MARKERS`: *договор, статья, кодекс, ТК, НК, ГК, ФЗ, неустойка, штраф, аренда, НДС* и т.д.), проверяются паттерны самопрезентации (*«что ты умеешь»* → `RESPONSE_ABOUT_ASSISTANT`, не считается отказом: `refused=False`) и бытового оффтопа (*«рецепт пиццы»*, *«какая погода»* → `RESPONSE_OUT_OF_SCOPE`). Наличие юридического маркера защищает сложные запросы от ложного срабатывания бытового фильтра.

#### Стадия 1. Разрешение истории диалога, анализ запроса и резолвинг сущностей (`query_analysis.py`, `entity_resolver.py`)
Если запрос прошел префильтр, вызывается `analyze_query()`:

1. **Разрешение кореференции и истории диалога (`_resolve_history_with_usage`)**:
   - Если передан `chat_history` (или в тексте запроса обнаружен инлайн-транскрипт диалога), система сначала проверяет через `is_independent_query()`, не является ли новый вопрос полностью самостоятельным (например, содержит явный номер нового договора или название кодекса без анафорических местоимений *«по нему»*, *«в этом договоре»*, *«тогда»*).
   - Если запрос зависит от контекста беседы, последние `MAX_HISTORY_TURNS` (6) реплик очищаются от инъекционных токенов и старых тегов `<source>` и передаются в LLM с промптом `HISTORY_RESOLUTION_SYSTEM`.
   - LLM переписывает вопрос в самодостаточный поисковый запрос, подставляя номер договора, контрагента и дату события из истории, но **не перенося конкретные суммы или проценты из прошлых ответов ассистента** (чтобы они не стали ложными предпосылками).
2. **Структурный разбор запроса (`QUERY_ANALYSIS_SYSTEM`)**:
   - LLM анализирует запрос и возвращает JSON, валидируемый схемой `QueryAnalysisSchema`:
     - `intent`: `exact_lookup`, `semantic`, `mixed`, `compare`, `date_version`, `checklist` или `out_of_scope`;
     - `task_type`: `lookup`, `explain`, `compare`, `checklist`, `date_check`, `premise_check`;
     - `entities_raw`: упомянутые номера договоров, названия контрагентов, кодексов или регламентов;
     - `article_refs`: номера статей и пунктов (например, `["70", "3.2", "13.11"]`);
     - `dates` и `event_date`: даты в формате `YYYY-MM-DD`;
     - `premises`: численные или фактологические утверждения пользователя в вопросе (суммы, сроки, ставки, даты);
     - `required_slots`: строго те правовые аспекты, о которых прямо спросил пользователь (из 21 поддерживаемого слота: `rent_amount`, `security_deposit`, `payment_deadline`, `penalty`, `accrual_period`, `liability_cap`, `probation_period`, `overtime_limit`, `overtime_pay`, `approval_process`, `termination`, `tax_rate`, `effective_date`, `delivery_terms`, `acceptance_terms`, `warranty_period`, `prepayment`, `return_procedure`, `document_handover`, `consent_withdrawal`, `seasonal_work`);
     - `decomposition`: список подвопросов `SubQuestion` для составных или сравнительных запросов;
     - `rewritten_queries_bm25` и `rewritten_queries_dense`: поисковые переформулировки.
3. **Жесткая пост-санитизация выхода LLM**:
   - **Защита от завышения `exact_lookup` (`_sanitize_intent`)**: если LLM поставила `exact_lookup` только потому, что в запросе есть номер договора, но в тексте нет номера пункта/статьи или просьбы о дословной цитате, интент автоматически понижается до `semantic`.
   - **Фильтрация «галлюцинированных» слотов (`_sanitize_required_slots`)**: регулярные выражения проверяют, действительно ли пользователь спрашивал про каждый слот. Например, во фразе *«какой размер пеней за просрочку арендной платы»* слова *«арендной платы»* характеризуют пени; функция `_asks_rent_amount()` вырезает упоминания аренды в контексте просрочки/срока и удаляет ошибочно добавленный LLM слот `rent_amount`, оставляя только `penalty`. Аналогично исправляется частая путаница между `prepayment` (аванс) и `security_deposit` (обеспечительный платеж).
   - **Гарантия покрытия слотов поисковыми запросами (`_ensure_slot_queries`)**: для каждого активного слота проверяется наличие дискриминативных словооснов (`_SLOT_DISCRIMINATIVE_STEMS`) в сгенерированных запросах. Если какой-то слот не покрыт, автоматически достраивается специализированный запрос по шаблону `_SLOT_QUERY_TEMPLATES` с учетом контекста (например, для КоАП/законов слот `penalty` разворачивается в *«размер административного штрафа ответственности санкции»*, а для неарендных договоров `payment_deadline` использует нейтральный шаблон без слов об аренде).
   - **Защита предпосылок от утечки ответов ассистента (`_filter_assistant_injected_premises`)**: если числовая предпосылка появилась после резолва истории, но этих цифр не было ни в текущем, ни в предыдущих сообщениях самого пользователя, она отбрасывается.
4. **Резолвинг документов и контрагентов (`entity_resolver.py`)**:
   - По `chunks.jsonl` и `indexing_manifest.json` строится кэшируемый каталог документов (`_load_document_catalog`). Для каждого документа сохраняются нормализованный заголовок, номер договора, алиасы версий и `haystack` — текст первых трех чанков (преамбулы) и фрагментов с организационно-правовыми формами (`ООО`, `АО`, `ПАО`, `ИП` и т.д.).
   - Это позволяет находить договор по названию контрагента, даже если в заголовке файла указан только номер договора, а название компании встречается лишь в преамбуле текста!
   - Применяется проверка границ слов (`(?<![0-9a-zа-я])...(?![0-9a-zа-я])`), чтобы названия не смешивались, а при отсутствии точного совпадения запускается нечеткий поиск через `rapidfuzz` (`fuzz.partial_ratio` и `fuzz.token_set_ratio`, порог кандидатов `85.0`, автопринятие единственного кандидата `>= 90.0`).
   - Правило маршрутизации (`extract_doc_routing_sets`):
     - Если сущность однозначно разрешилась в один документ (`resolved=True`) → его ID попадает в жесткий фильтр `selected_doc_ids`.
     - Если найдено несколько подходящих документов (неоднозначность) → поиск **не сужается** (`selected_doc_ids=None`), а все кандидаты передаются в мягкий бустинг `boost_doc_ids`.
5. **Regex-fallback**: если LLM на этапе анализа вернула невалидный JSON после всех попыток, функция `_build_regex_fallback_spec()` собирает полноценный `QuerySpec` чисто алгоритмически (извлекая кавычки, номера договоров, статьи, русские даты и слоты регулярными выражениями) с пометкой `degradation_reason="regex_fallback"`.

#### Стадия 2. Планирование поиска и определение назначения источников (`planner.py`, `source_kind.py`)
Планировщик `planner.plan(spec, selected_doc_ids)` формирует поисковое задание `RetrievalTask`:
1. **Определение требуемых типов источников (`detect_required_source_kinds`)**:
   - Слоты и текстовые маркеры запроса сопоставляются с двумя ролями источников:
     - `normative` (нормативное основание → типы документов `law`, `internal`): слоты `approval_process`, `tax_rate`, `overtime_limit`, `overtime_pay`, `probation_period`, `consent_withdrawal`, `seasonal_work`, `document_handover`, а также маркеры *«регламент», «положение», «порядок согласования», «закон», «статья»*;
     - `specific` (документ сделки → тип документа `contract`): слоты `rent_amount`, `security_deposit`, `payment_deadline`, `penalty`, `accrual_period`, `liability_cap`, `termination`, `delivery_terms`, `acceptance_terms`, `warranty_period`, `prepayment`, `return_procedure`, `effective_date`, а также маркеры *«условия договора», «контрагент», «поставщик», «арендатор»* и т.д.
   - Если запрос требует только нормативного основания, поиск будет отфильтрован по `{"law", "internal"}`; если только условий сделки — по `{"contract"}`; если вопрос комплексный (например, *«нужно ли одобрение гендиректора для этого договора поставки и какова сумма сделки»*), список `required_source_kinds` будет содержать оба типа `["normative", "specific"]`.
2. **Консолидация в единый Hybrid-запрос (`_combined_hybrid_query`)**:
   - Вместо запуска множества конкурирующих мелких задач планировщик собирает дедуплицированный (с отсечением вложенных подстрок через `_merge_query_parts`) единый запрос из `dense_rewrites`, `bm25_rewrites`, `slot_expansions`, `decomposition` и (для `date_version`) маркеров дополнительных соглашений.
   - Интент запроса маппится в весовой профиль гибридного поиска (`exact_lookup`, `semantic_query` или `mixed_query`).

#### Стадия 3. Гибридный поиск, темпоральная фильтрация и реранкинг (`bridge.py`, `hybrid.py`, `reranker.py`)
Модуль `bridge.retrieve_tasks()` исполняет поисковую задачу через `hybrid.py`:

1. **Прогрев бэкендов (`prewarm_retrieval_backends`)**:
   - При первом вызове потокобезопасно инициализирует коллекцию ChromaDB, проверяет совпадение размерности сохраненных эмбеддингов с ожидаемой (`1024`) и отправляет 4 коротких прогревочных запроса на HTTP-сервер эмбеддингов, чтобы исключить холодный старт.
2. **Темпоральное разрешение и фильтрация версий (`resolve_allowed_versions_by_date` и `select_dominant_versions`)**:
   - Определяется дата проверки `check_date` (`resolve_check_date_details`):
     - Если передан или найден в запросе/истории точный `event_date` → режим `historical`, точность `day`.
     - Если в вопросе указан только год (например, *«в 2024 году»*, при этом годы внутри номеров договоров вроде `ДП-10/2024` предварительно вырезаются регуляркой `_CONTRACT_NUMBER_RE`) → берется середина года `{year}-06-01`, режим `historical`, точность `year`.
     - Иначе берется сегодняшняя дата → режим `current`, точность `day`.
   - Если заданы `selected_doc_ids`, к ним автоматически добавляются все дополнительные соглашения, у которых `amends_document_id` указывает на выбранный договор!
   - Для каждого чанка вычисляется статус редакции `effective_status(chunk, check_date)` по полуинтервалу `effective_from <= check_date < effective_to`:
     - `applicable` — редакция действовала на дату проверки (включается в поиск);
     - `current_only` — событие произошло раньше `effective_from` закона (`document_type == "law"`), но в базе есть только текущая редакция закона (включается в поиск с предупреждением);
     - `unknown` — даты действия неизвестны (не исключается из поиска, но помечается в `validity_unknown`);
     - `not_applicable` — договор еще не вступил в силу на дату события или редакция уже утратила силу (жестко исключается из поиска).
   - **Выбор доминирующей версии (`select_dominant_versions`)**: если у одного документа (`document_id`) есть несколько версий (`version_id`), система выбирает наиболее приоритетную версию (`applicable` с максимальной датой `effective_from <= check_date` → `current_only` → `unknown`), чтобы в выдачу никогда не попадали две взаимоисключающие редакции одного документа одновременно.
3. **Раздельный поиск по ролям источников**:
   - Если задача требует одновременно и `normative`, и `specific` источники, `_run_single_task()` выполняет гибридный поиск **отдельно для каждой роли** (с передачей `document_types` в BM25 и в `where`-фильтр ChromaDB), чтобы высокочастотные чанки договора не вытеснили чанки регламента или закона из топ-выдачи.
4. **Двухканальный поиск и взвешенный RRF (`hybrid_search`)**:
   - В зависимости от интента выбираются веса и глубина кандидатов (`_INTENT_WEIGHTS`):

| Профиль намерения | Вес BM25 (`w_bm25`) | Вес Dense (`w_dense`) | Глубина `bm25_top` | Глубина `dense_top` |
| :--- | :--- | :--- | :--- | :--- |
| **`exact_lookup`** (номера статей/пунктов) | `0.7` | `0.3` | `40` | `20` |
| **`mixed_query`** (сравнение, версии, смешанный) | `0.5` | `0.5` | `30` | `30` |
| **`semantic_query`** (смысловые вопросы) | `0.3` | `0.7` | `20` | `40` |

   - **Канал 1 (BM25)**: `bm25_store.search_with_stats()` за один проход считает скоры `BM25Okapi`, отсекает чанки вне `allowed_chunk_ids` и возвращает топ-кандидатов вместе со статистикой фильтрации.
   - **Канал 2 (Dense Vector)**: вычисляет эмбеддинг запроса (`get_query_embedding` с поддержкой ретраев, экспоненциального backoff и `hash_fallback` в локальном режиме при недоступности сервера), строит `where`-фильтр ChromaDB по `document_id`, `version_id` и `document_type` и запрашивает ближайших соседей.
   - **Агрегация (Weighted Reciprocal Rank Fusion)**: скор каждого чанка вычисляется по формуле:
     $$\text{score}(c) = \frac{w_{\text{bm25}}}{k + \text{rank}_{\text{bm25}}(c) + 1} + \frac{w_{\text{dense}}}{k + \text{rank}_{\text{dense}}(c) + 1}, \quad k = 60$$
   - **Условный буст дополнительных соглашений (`should_boost_amendments`)**: если в запросе явно упоминаются *«дополнительное соглашение», «редакция», «изменения»* (или интент `date_version`), чанки с непустым `amends_document_id` получают множитель `* 1.15`.
   - **Мягкий буст неоднозначных документов (`DOC_BOOST_FACTOR`)**: в `bridge._finalize_single_task_results()` чанки документов из `boost_doc_ids` получают однократный множитель `* 1.1`, а топ-3 чанка защищаются от вытеснения (`protected_top_ids`).
5. **Нейросетевой реранкинг (`reranker.py` и `bridge.rerank_chunks`)**:
   - Пул кандидатов (до 40 чанков) передается в реранкер `Qwen/Qwen3-Reranker-8B` со специализированной юридической инструкцией (`_RERANKER_INSTRUCTION`).
   - **Защита представительства типов источников (`_preserve_source_kind_representation`)**: если запрос требовал одновременно `normative` и `specific`, а реранкер оставил в `top_n` (по умолчанию 5) только один тип, оркестратор автоматически возвращает лучший дореранковый чанк пропавшего типа в конец списка!

#### Стадия 4. Оценка доказательств и адаптивный Follow-up (`evidence.py`)
Модуль `evidence.assess(spec, chunks)` анализирует качество найденных чанков перед генерацией:
1. **Отсечение пустых/слабых чанков (`_extract_substantive_body`)**:
   - Чанки со скором `< 0.005` или содержащие только строку заголовка раздела без содержательного текста нормы (`< 25` символов после удаления заголовков) не считаются пригодными (`viable_chunks`).
   - Если `viable_chunks_count == 0`, оркестратор **немедленно возвращает штатный отказ** `no_relevant_documents` без вызова генератора и верификатора (экономия времени и токенов).
2. **Проверка покрытия слотов (`_slot_matches`)**:
   - Для каждого слота из `spec.required_slots` проверяется наличие ключевых маркеров в тексте пригодных чанков: слот считается покрытым, если найдено хотя бы 1 сильное ключевое выражение (`SLOT_KEYWORDS_STRONG`) или минимум 2 обычных термина из `SLOT_KEYWORDS`.
3. **Детектирование и разрешение численных противоречий (`_detect_contradictions`)**:
   - Если на один слот претендуют два и более чанка **с одинаковым `provision_id`** (например, базовая редакция пункта договора и допсоглашение к тому же пункту), регулярные выражения сравнивают извлеченные суммы в рублях, проценты и сроки в днях/месяцах/часах.
   - При обнаружении разных чисел вызывается LLM (`_resolve_contradictions_with_llm`, промпт `EVIDENCE_CONTRADICTION_SYSTEM`), которая определяет: является ли расхождение реальным неразрешимым противоречием (`is_real_contradiction: true`) или это штатная правовая ситуация (например, допсоглашение изменило базовый договор или установлены разные сроки для разных категорий работников).
4. **Проверка версионных проблем и предупреждений (`_collect_version_warnings`)**:
   - Формируются структурированные предупреждения для генератора (`generation_warnings`): `only_current_revision_available`, `validity_unknown`, `approximate_event_date`, `invalid_event_date`, `missing_source_kind`.
5. **Follow-up цикл дозапроса**:
   - Если `sufficiency == INSUFFICIENT` или остались непокрытые слоты (`missing_slots`), при этом **не было технического сбоя поиска** и есть хотя бы один пригодный чанк (`viable_chunks_count > 0`), оркестратор запускает до `MAX_FOLLOWUP_RETRIEVAL_CYCLES` (1) дополнительный цикл `planner.followup()`, формирующий расширенный запрос специально по недостающим слотам, и объединяет новые чанки с ранее найденными.

#### Стадия 5. Политика безопасности, проверка предпосылок и сборка контекста (`precheck.py`, `context_builder.py`)

1. **Защита от косвенных инъекций в документах (`precheck.py`)**:
   - Каждый найденный чанк проверяется на паттерны `_CHUNK_INJECTION_PATTERNS` (*«игнорируйте все другие документы»*, *«новое системное правило»*, *«изменить порядок ответов»*).
   - Если вредоносная строка найдена, она вырезается из текста чанка. Если после очистки осталось `>= 40` символов нормального текста, чанк сохраняется очищенным; иначе ему выставляется флаг `untrusted = True`.
2. **Детерминированная верификация предпосылок пользователя (`_evaluate_premise`)**:
   - Недоверенные чанки (`untrusted=True`) полностью исключаются из проверки предпосылок.
   - Каждая числовая/календарная предпосылка пользователя (`amount`, `term`, `rate`, `date`) приводится к каноническому виду (`_normalize_value`: например, `"450 тыс. руб."` → `"450000"`, `"5 рабочих дней"` → `"5d"`, `"15 мая 2024"` → `"2024-05-15"`).
   - Из текста предпосылки извлекаются 5-буквенные основы значимых слов — **якоря параметра** (`_extract_anchors`, за вычетом стоп-корней вроде *«догов», «сумм», «разм»*).
   - В предложениях доверенных чанков ищутся совпадения по якорям и совместимым периодам времени (`_period_compatible`), при этом разные единицы измерения сроков (дни vs месяцы vs часы) никогда не сравниваются между собой.
   - Присваивается один из трех статусов (`PremiseStatus`):
     - `VERIFIED` — в предложении с теми же якорями найдено точно такое же нормализованное значение;
     - `CONTRADICTED` — в предложении с теми же якорями и совместимым периодом найдено ровно одно однозначное другое значение (фиксируется `conflicting_value` и `evidence_source_id`);
     - `UNKNOWN` — якоря не найдены, единицы несопоставимы или в тексте несколько разных чисел. **Статус `UNKNOWN` строго запрещено трактовать как ошибку пользователя**.
3. **Форматирование контекста (`build_context_and_sources`)**:
   - Каждому чанку присваивается короткий идентификатор источника `S1`, `S2`, ..., `Sn`.
   - В текст контекста для LLM (`CONTEXT_ITEM_TEMPLATE`) передаются только подтвержденные метаданные (если статус редакции `unknown`, строка `Редакция:` скрывается, чтобы модель не выдала неподтвержденный период действия за факт):
     ```text
     [S1] Договор аренды нежилого помещения № 15-2024/АР
     Раздел: 3. Порядок расчетов -> Пункт 3.2
     Пункт/Статья: 3.2
     Редакция: действует с 2024-02-01 по настоящее время
     Назначение источника: документ сделки
     Статус редакции: действует на текущую дату
     Текст:
     ...
     ```
   - Одновременно формируется словарь `sources[source_id]` с полными координатами чанка (`location`: страницы, строки, символы), подгружаемыми из кэша `chunks.jsonl`.

#### Стадия 6. Генерация черновика ответа (`generator.py`)
Функция `generate_draft()` вызывает LLM с промптом `GENERATION_SYSTEM` (`temperature = 0.2`), передавая вопрос, санитизированную историю диалога, контекст `[S1]..[Sn]`, статусы предпосылок (`premise_statuses`), предупреждения о версиях и флаг `refusal_forbidden` (запрет на полный отказ, если `sufficiency == SUFFICIENT`).

LLM обязана вернуть валидный JSON по схеме `DraftAnswerSchema`:
- `answer_text`: лаконичный (1–4 предложения) прямой ответ строго на заданный вопрос с инлайн-тегами `<source>S1</source>` после каждого факта;
- `claims`: массив атомарных утверждений `{text, source_ids, slot}`, каждое из которых **дословно** подтверждается указанным источником;
- `assumptions`: любые толкования «по смыслу» (с префиксом `"интерпретация: ..."`) и допущения по датам;
- `missing_info`: заполняется только если часть прямо спрошенного пользователем вопроса отсутствует в контексте (если ответ найден, список обязан быть пустым `[]`);
- `refusal_reason`: заполняется только если в контексте вообще нет данных по теме вопроса.

При ошибке парсинга JSON выполняется повторная попытка с обратной связью (`MAX_ATTEMPTS_GENERATE_INITIAL = 2`), а при полном исчерпании попыток срабатывает безопасный `draft_raw_fallback`.

#### Стадия 7. Двухконтурная верификация и цикл регенерации (`verification.py`, `generator.py`)
Функция `verify()` в `verification.py` сочетает LLM-аудит и жесткие алгоритмические инварианты:

1. **Синтез claims при их отсутствии (`_synthesize_claims_from_answer`)**:
   - Если генератор вернул `answer_text` с тегами `<source>S1</source>`, но оставил список `claims` пустым, верификатор автоматически разбивает текст ответа на предложения и синтезирует проверяемые `Claim` из каждого предложения с тегом источника. Если в ответе нет ни `claims`, ни тегов `<source>`, блокируется автопринятие (`auto_accept_blocked = True`) и выставляется вердикт `PARTIAL`.
2. **Независимый LLM-аудит (`VERIFIER_SYSTEM`, `temperature = 0.0`)**:
   - Проверяет каждое утверждение `claim_idx` против текста источников и присваивает статус:
     - `supported` — буквальное подтверждение всех чисел, сроков и условий в цитируемом фрагменте;
     - `not_in_source` — отсутствие буквального подтверждения или расширительное толкование;
     - `contradicted` — прямое противоречие с текстом источника (с обязательной цитатой `quote`).
   - Выполняет отдельную проверку **`answer_to_question`**: отвечает ли `answer_text` на **исходный вопрос пользователя** (`match`, `mismatch`, `undetermined`), не подменил ли генератор объект вопроса (другой договор, другой параметр).
3. **Алгоритмические проверки поверх вердикта LLM**:
   - **Валидность ссылок**: если `source_id` отсутствует в `source_map`, статус принудительно переводится в `NOT_IN_SOURCE` и фиксируется ошибка в `citation_errors`.
   - **Контроль назначения источника (`_source_role_mismatch`)**: если запрос содержит один целевой слот (например, нормативный слот `overtime_limit`), а утверждение опирается исключительно на чанки с противоположной ролью (`specific` / договор), статус `SUPPORTED` аннулируется (`NOT_IN_SOURCE`, причина `source_role_mismatch`).
   - **Защита от недоверенных чанков**: если утверждение опирается только на чанк с флагом `untrusted=True` и не подтверждено ни одним доверенным чанком, оно отклоняется (`NOT_IN_SOURCE` + запись в `injection_signals`).
   - **Темпоральный инвариант**: если задан `event_date` и все цитируемые чанки (кроме законов в режиме `current_only`) вступили в силу позже даты события или утратили силу раньше нее, статус переводится в `CONTRADICTED`.
   - Все утверждения, прошедшие все проверки со статусом `SUPPORTED`, заносятся в список **`supported_locked`**.
4. **Принятие решения (`VerificationVerdict`)**:
   - `REGENERATE`: если обнаружен `answer_to_question == MISMATCH` или есть исправимые ошибки (`CONTRADICTED`, `NOT_IN_SOURCE`, `citation_errors`) и доступен цикл регенерации (`MAX_REGENERATE_CYCLES = 1`).
   - `ACCEPT`: все утверждения `SUPPORTED`, нет ошибок цитирования, `answer_to_question == MATCH`, нет опровергнутых предпосылок и текст ответа согласован со списком `claims`.
   - `PARTIAL`: часть утверждений подтверждена (`any_supported`). В этом случае **неподтвержденные утверждения и предложения без подтвержденных источников автоматически вырезаются из текста ответа** (`_prune_answer_to_supported_sources`), а сами неподтвержденные тезисы переносятся в `assumptions` с пометкой `"интерпретация: ..."`.
   - `REFUSE`: ни одно утверждение не подтверждено или `answer_to_question == MISMATCH` после регенерации.
5. **Регенерация (`regenerate_draft`)**:
   - При вердикте `REGENERATE` вызывается `regenerate_draft()` с промптом `REGENERATE_SYSTEM`.
   - На уровне кода функция `_enforce_supported_locked()` гарантирует, что все ранее подтвержденные утверждения из `supported_locked` **сохранят свой дословный текст и валидные источники**, даже если LLM попытается их исказить или удалить.
   - Затем проверяется инвариант согласованности `_validate_draft_consistency()`. Если LLM нарушила консистентность или произошел сбой, срабатывает детерминированный безопасный фоллбэк `_build_safe_regen_fallback()`:
     - **Сценарий A** (есть `supported_locked`): ответ собирается строго из текстов подтвержденных утверждений;
     - **Сценарий B** (нет `supported_locked`): возвращается контролируемый отказ `verification_failed`.

#### Стадия 8. Финальная сборка ответа и расчет уверенности (`assemble_final`)
На заключительном этапе `assemble_final()` в `orchestrator.py`:
1. Очищает теги `<source>...</source>` от несуществующих идентификаторов и собирает список реально процитированных источников `cited_ids`.
2. Оставляет в словаре `result.sources` только те источники, которые реально подкрепляют ответ (при отказе `sources` очищается до `{}`).
3. Вычисляет итоговый уровень уверенности `confidence` (`high`, `medium`, `low`) и список причин `confidence_reasons` (`_compute_confidence_and_reasons`):
   - `high`: ответ не является отказом, нет деградаций, `missing_info` пуст, верификация прошла чисто;
   - `medium`: частичное покрытие (`missing_info`), некритичные деградации или ошибки цитирования;
   - `low`: отказ (`refused=True`), недоступность верификатора (`verifier_unavailable`) или `answer_question_mismatch`.
4. При необходимости форматирования тегов `<source>S1</source>` в человекочитаемый текст используется утилита `replace_source_tags(answer, sources)` из `context_builder.py`:
   - если источник упомянут в тексте **1 раз**, тег заменяется инлайн на `[Источник: <Название документа, Раздел, Статья>]` (при этом функция `_is_covered_by_title()` умно убирает дублирование, если номер статьи уже входит в заголовок файла);
   - если источник цитируется **2 и более раз**, все инлайн-теги этого источника удаляются (с подчисткой лишних пробелов перед знаками препинания), а сам источник выносится один раз в финальный блок `Источники:` в конце ответа.

### Обработка технических сбоев и Bailout (`refusal.py`, `bailout.py`)
Оркестратор строго различает три разные ситуации, когда полный ответ невозможен:
1. **Штатное отсутствие данных в базе (`RESPONSE_REFUSAL_NO_CONTEXT`)**: поиск отработал штатно, но документов по вопросу нет (`no_relevant_documents` или `insufficient_evidence`).
2. **Технический сбой поиска (`RESPONSE_RETRIEVAL_ERROR`)**: в `bridge.retrieve_tasks` произошла инфраструктурная ошибка или таймаут (`technical_retrieval_failure = True`), и частичных данных недостаточно. В этом состоянии **follow-up цикл подавляется**, а пользователь получает честное сообщение о временной технической ошибке поиска с рекомендацией повторить запрос, а не ложный ответ «в базе нет сведений».
3. **Превышение бюджета времени или ошибок (`bailout.explain`)**: если запрос прервался по общему дедлайну `REQUEST_TOTAL_TIMEOUT_S` или лимиту сбоев LLM, но этап `query_analysis` уже успел распознать сущности (`partial_spec`), модуль `bailout.py` формирует вежливое резюме: какие именно договоры/статьи/даты система успела распознать и как лучше упростить или уточнить запрос.

### Структура возвращаемого объекта `AgentResult`

| Поле | Тип | Описание |
| :--- | :--- | :--- |
| `final_answer` | `str` | Итоговый ответ ассистента с валидированными тегами `<source>S1</source>` (или текст шаблона отказа) |
| `sources` | `dict[str, dict]` | Словарь только реально процитированных источников (`S1`, `S2`...) с полями `document_id`, `version_id`, `chunk_id`, `document_title`, `provision_id`, `structure_path`, `text`, `location` (`page`, `start_line`, `end_line`, `char_start`, `char_end`), `score`, `effective_from`, `effective_to`, `amends_document_id` |
| `intent` | `str` | Распознанное намерение запроса (`exact_lookup`, `semantic`, `mixed`, `compare`, `date_version`, `checklist`, `out_of_scope`, `about_assistant`) |
| `refused` | `bool` | Флаг отказа от ответа (`True` при отсутствии данных, блокировке префильтром, сбое поиска или провале верификации) |
| `refusal_reason` | `str \| None` | Машиночитаемый код причины отказа (`prompt_injection`, `illegal`, `out_of_scope`, `no_relevant_documents`, `insufficient_evidence`, `retrieval_error`, `verification_failed`, `llm_unavailable`, `cannot_parse`) |
| `confidence` | `str` | Оценка надежности ответа: `"high"`, `"medium"` или `"low"` |
| `assumptions` | `list[str]` | Список правовых интерпретаций сверх буквального текста источника и допущений по датам |
| `missing_info` | `list[str]` | Аспекты вопроса пользователя, которые не удалось подтвердить источниками |
| `verification` | `VerificationReport \| None` | Полный отчет верификатора со статусами каждого `Claim`, цитатами, результатом `answer_to_question` и списком `supported_locked` |
| `query_spec` | `QuerySpec \| None` | Полная спецификация разобранного запроса (слоты, сущности, предпосылки со статусами `VERIFIED`/`CONTRADICTED`/`UNKNOWN`, декомпозиция) |
| `degradation_reasons` | `list[str]` | Список сработавших фоллбэков (`regex_fallback`, `no_effective_dates`, `retrieval_partial_failure`, `regen_fallback` и др.) |
| `used_history` | `bool` | Была ли задействована история диалога для переформулирования запроса |
| `trace` | `list[TraceStep]` | Пошаговый лог выполнения всех этапов пайплайна с таймингами, токенами и редактированной диагностикой (без утечки API-ключей и путей) |

## 4. Запуск решения

### 1. Клонирование репозитория

Склонируйте репозиторий и перейдите в корневую директорию проекта:

```
git clone <URL_РЕПОЗИТОРИЯ>
cd hackathon-psb
```

Для запуска решения необходимо, чтобы на компьютере были установлены:

- Docker;
    
- Docker Compose (Docker Compose V2).
    

Проверить корректность установки можно командами:

```
docker --version
docker compose version
```

### 2. Подготовка окружения и переменных среды

Cоздайте файл `.env` в корне проекта на основе шаблона `.env.example`:

```
cp .env.example .env
```

Заполните необходимые параметры подключения к LLM-провайдеру и сервисам эмбеддингов и реранкинга:

```
LLM_BASE_URL=https://api.your-llm-provider.local/v1
LLM_API_KEY=sk-...
LLM_MODEL=deepseek-ai/DeepSeek-V4.1-Flash

# Локальный llama.cpp сервер эмбеддингов
EMBEDDING_API_BASE_URL=http://127.0.0.1:8082/v1
EMBEDDING_API_KEY=local
EMBEDDING_MODEL=bge-m3

# HTTP-эндпоинт реранкера
RERANKER_API_BASE_URL=https://api.your-llm-provider.local/v1
RERANKER_API_KEY=sk-...
RERANKER_MODEL=Qwen/Qwen3-Reranker-8B
```

> **Примечание об офлайн-токенизации:** модуль `rag_core/indexing/tokenizer_utils.py` автоматически ищет предзагруженный BPE-словарь `cl100k_base` (`9b5ad71b2ce5302211f9c61530b329a4922fc6a`) в каталоге `tiktoken_cache/` и выставляет `TIKTOKEN_CACHE_DIR` до инициализации `tiktoken`. Благодаря этому токенизация работает без обращения к внешнему интернету.

### 3. Необязательный этап — сборка поисковых индексов

> **В репозитории уже содержатся готовые поисковые индексы и векторные коллекции. Поэтому повторную сборку выполнять не требуется.**

При необходимости пересоздания индексов поместите исходные документы в `data/raw/` и выполните:

```
python build_index.py
```

Скрипт создаст:

- `data/processed/chunks.jsonl` — канонические чанки со структурой и локациями;
    
- `storage/bm25_index/bm25.pkl` — лексический индекс BM25Okapi;
    
- `storage/chroma_db/` — векторную коллекцию ChromaDB;
    
- `data/manifests/indexing_manifest.json` — манифест сборки.
    

Для неразрушающей сверки консистентности между `chunks.jsonl`, ChromaDB и BM25 можно вызвать `check_index_consistency()` из `rag_core.retrieval.hybrid`.

### 4. Сборка и запуск приложения

После подготовки конфигурации перейдите в корневую директорию проекта и выполните:

```
docker compose up --build
```

Команда автоматически:

- соберёт Docker-образы приложения;
    
- установит необходимые зависимости;
    
- запустит backend на базе FastAPI;
    
- запустит frontend;
    
- настроит взаимодействие между frontend и backend;
    
- выполнит проверку готовности backend перед запуском frontend.
    

При первом запуске сборка Docker-образов может занять некоторое время.

После успешного запуска приложение будет доступно по следующиму адресу:
- http://localhost

Backend работает внутри Docker-контейнера на порту `8000`, а frontend доступен на порту `80`. Обращение к API осуществляется через frontend.

**Остановка приложения:**

Для остановки контейнеров нажмите `Ctrl + C` в терминале, а затем выполните:

```
docker compose down
```

Для повторного запуска без пересборки образов:

```
docker compose up
```

Для запуска в фоновом режиме:

```
docker compose up --build -d
```

Просмотреть логи работающих сервисов можно командой:

```
docker compose logs -f
```
